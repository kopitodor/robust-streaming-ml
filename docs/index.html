Robust streaming keyword spotting

A small log-mel CNN that classifies 10 spoken commands from Speech Commands v0.02, carried from a verified dataset manifest through calibrated held-out evaluation, controlled robustness testing, streaming-window inference, an ONNX export checked against PyTorch, and a documented CPU latency benchmark. Every number on this page is copied from RESULTS.md, where it traces to a recorded run and a protocol committed before that run.

Scope: a closed-set classifier for exactly 10 commands (yes, no, up, down, left, right, on, off, stop, go). It is not general speech recognition and has no silence or unknown-word rejection. It is a portfolio project, not production software, and makes no real-time or state-of-the-art claim.

Goal

Show how a small, understandable classifier behaves when audio is processed in realistic streaming windows and under controlled signal corruption, with every step reproducible and every reported number traceable. The aim is sound engineering practice rather than a leaderboard result: validated data splits, a documented baseline, calibration, robustness testing, deployment-oriented export, and honest measurement. See DESIGN.md for the bounded proposal and the acceptance-criteria status.

Architecture

  1. Acquire and verifySpeech Commands v0.02 archive pinned by SHA-256 and size; CC BY 4.0 licence recorded and signed off. record
  2. Validate and manifestStrict WAV parser, official speaker-disjoint splits (30,769 / 3,703 / 4,074), content-hash duplicate and leakage checks; manifest pinned by SHA-256. contract
  3. Features and model1 s window, 40-band log-mel (25 ms / 10 ms), and kws_cnn_v1: four conv blocks, 61,052 parameters. baseline
  4. TrainAdamW, 30 epochs, cosine schedule, seed 1234, deterministic; best checkpoint at epoch 18 by validation loss. Test split never loaded.
  5. Evaluate and calibrateHeld-out test metrics, confusion matrix, 15-bin ECE; temperature scaling fitted on validation only. protocol
  6. RobustnessNoise, reverberation, resampling, clipping, and Opus codec, 3 fixed severities each, with per-clip seeds. protocol
  7. Stream and export1 s windows every 100 ms, batch-1 inference, causal mean of the last 5 windows; ONNX opset 18 including the STFT front end. protocol
  8. Benchmark and demoCPU latency of the streaming step on ONNX Runtime; an offline local demo on the verified export. protocol

Reproducibility and provenance

  • Protocol first. Each evaluation, robustness, streaming/ONNX, and benchmark protocol was committed, with its parameters and tolerances, before its first real run; measured results were committed separately afterwards.
  • Every run is anchored. A single start_run entry point refuses a dirty tree or an unresolvable git revision, applies and verifies seeding, and records the commit, configuration hash, and environment.
  • Pins and fail-closed gates. The dataset archive, manifest, checkpoint, baseline reports, and ONNX export are pinned by SHA-256; a mismatch stops the run instead of being repaired or ignored.
  • Bit-exact reproduction gates. The robustness and export runs re-derive the held-out test logits bit-for-bit before measuring anything else.
  • Independent verification. For the evaluation, robustness, export, and benchmark runs, separate scripts re-hashed the artifacts and regenerated the reported statistics from the raw prediction, parity, and timing files.
  • Checks. Formatting, lint, strict type checking, the full test suite, and an isolated wheel-install check run before every commit; the full check was also rehearsed on CPython 3.10.

Streaming and ONNX parity

Protocols kw10-streaming-v1 and kw10-onnx-v1. The validated log-mel front end and CNN were exported with the PyTorch dynamo exporter at opset 18 (waveform [batch, 16000] → logits [batch, 10]); exporting twice gave byte-identical files. ONNX Runtime 1.30.0 on the CPU provider was compared with PyTorch window by window against tolerances fixed in advance from synthetic probes only.

Streaming consistency: on all 4,074 test clips, the ONNX streaming decision equals the clip-level prediction (4,074 / 4,074), with accuracy 0.9639. Audio was pushed in seeded random chunk sizes, and every streamed window was bit-identical to an independent offline reference windowing (tests cover arbitrary chunkings). Speech Commands clips are at most 1 s long, so each clip-as-stream has one window; the multi-window streams are artificial concatenations used for numerical parity only.

CPU latency

Protocol kw10-latency-v1, committed before measuring: batch size 1; a 1 s window every 100 ms of real test audio; 500 warm-up steps, then 5,000 individually timed steps (perf_counter_ns) per block, 3 interleaved repetitions (15,000 pooled steps); nearest-rank percentiles; raw timings kept. The primary path is one full streaming step: buffer update, window copy, ONNX Runtime inference including the log-mel feature extraction, softmax, and aggregation. Machine: AMD Ryzen 7 5800H (8 cores / 16 threads), Windows 11, ONNX Runtime 1.30.0, PyTorch 2.14.0 CPU; power, thermal state, and background load not controlled.

The PyTorch eager reference was faster than the ONNX export on this machine, and 4 threads did not help ONNX Runtime. A labelled diagnostic profile (outside the protocol) attributed about 81% of ONNX Runtime kernel time to its STFT operator. These are descriptive numbers for one laptop and one run, not a production service level or a real-time guarantee.

Local demo

An offline command-line demo streams a local 16 kHz mono 16-bit WAV file through the pinned, parity-verified ONNX export and writes a self-contained HTML page with per-window predictions, the causal aggregate, timing, and an optional comparison against one defined corruption. Nothing is uploaded and no server is used. It needs the locally generated export run; see docs/demo.md.

uv run python scripts/demo.py --audio path/to/clip.wav --corruption noise --severity snr_10db --open

Limitations

  • Closed set of 10 commands: every input, including silence, noise, and other words, receives one of the 10 labels. No silence or unknown-word rejection; not general speech recognition.
  • One model, one training seed, one corruption draw per clip: no confidence intervals.
  • Official test numbers include 121 redundant duplicate copies (a de-duplicated view is reported separately); near-duplicates are not detected.
  • Trained and evaluated on isolated 1 s clips; behaviour on continuous or real-world audio, other microphones, accents, or recording conditions was not evaluated.
  • Robustness corruptions are synthetic (white noise, synthetic room responses, one resampler, symmetric clipping, one codec family).
  • ONNX parity was measured on clean test audio; the multi-window streams are artificial concatenations.
  • Latency comes from one uncontrolled laptop, one runtime version, and one run.
  • Bit-exact reproducibility is established only on the recorded platform and library versions (Windows, CPython 3.14.2); the GitHub Actions workflow has not yet run.
  • Not production software; no reliability, real-time, or state-of-the-art claim.
